### 1.4 技術的負債

- **プロトコル未定義**: TCP/UDPの選択、パケットフォーマット(バイナリ/テキスト)、エンディアン、フレーミング、エラーコードが未決定。監視制御の成否を左右する最重要の未決事項。
- **言語方針の矛盾**: READMEは「C言語」を示唆するが、要求は「Windows GUIアプリ + Ethernet通信 + 保守性」。C言語のままGUIを書くとWin32 API直書きになり保守性が低い。言語選定から合意が必要(§4参照)。
- **対向デバイス仕様なし**: 監視対象(PLC? 組込み機器? PC?)が未定義。シミュレータの自作が前提となる可能性が高い。
- **Windows固有**: Devinの本VMはLinux。Windows子セッション(Windowsプラットフォーム)での実機検証、またはCI上のwindowsランナーでのビルド検証が前提となる。

## 3. リスク分析

| リスク | 影響 | 対策 |
|---|---|---|
| 通信断(ケーブル抜け、デバイス停止) | 監視データ欠損、制御不可 | ハートビート+タイムアウトで検知。受信タイムアウト時にUIへ「切断」状態を明示。制御コマンドは送信前に接続状態を検証 |
| 再接続 | 頻繁な再接続でログ氾濫・制御遅延 | 指数バックオフ(1s→最大30s)+ジッター。切断期間のデータ欠損をUIに表示。自動/手動再接続を設定可能に |
| パケット異常(破損・分割・順序異常) | 誤動作・誤表示 | フレーミング(長さプレフィックスまたはマジック+CRC)。不正パケットは破棄してログ。CRCエラー率を監視指標化。TCPはストリームなので境界処理を厳密化(部分受信・Nagle対策) |
| GUIフリーズ | 操作不能、監視空白 | **UIスレッドでブロッキングI/Oを絶対しない**。通信は専用スレッド、UIへの反映はメッセージキュー経由。長時間処理はキャンセル可能に |
| メモリリーク | 長時間運転で不安定化 | RAII/スマートポインタ(.NETはGCに依存だがイベント購読解除を徹底)。ASan/静的解析をCIに組込み。長時間試験でメモリ使用量を記録・閾値監視 |
| その他: Windows依存 | Linux CIでビルド不可 | windows-latest ランナー、またはWindows子Devinでの検証 |

## 4. 推奨アーキテクチャ

### 4.1 候補比較

| 観点 | A: Win32 API (C) | B: MFC (C++) | C: .NET 8 + WPF (C#) | D: Qt (C++) |
|---|---|---|---|---|
| 実装言語 | C | C++ | C# | C++ |
| 開発生産性 | 極めて低い | 低い | 高い | 中〜高 |
| GUI表現力 | 最小限 | 旧式 | 高い(DataBinding, MVVM) | 高い |
| 通信実装 | Winsock直書き | CAsyncSocket等 | `System.Net.Sockets`/非同期async | QTcpSocket |
| テスト性 | 悪い | 悪い | 良い(単体テスト容易、DI可能) | 中 |
| 保守性 | 低い | 低い(縮小技術) | **高い**(人材・情報・CI充実) | 中〜高(ライセンス要検討) |
| ライセンス/配布 | 自由 | 自由 | 自由(自己完結配布可) | GPL/商用ライセンス注意 |
| 長時間安定運用 | 自作次第 | 自作次第 | GC管理で安定 | 自作次第 |
| Devinの検証 | Windows必須 | 同 | Windows必須(※Linuxでビルドも可能だがWPF実行はWindows) | 同 |

### 4.2 提案: **C — .NET 8 + WPF (C#)**

監視制御ソフトとして最も保守しやすい構成。

**根拠:**
- MVVM + DIでGUIとロジックを分離でき、通信レイヤをGUIなしで単体テスト可能。Phase 2/4(通信実装・試験自動化)と相性が良い。
- `async/await`による非同期通信が言語機能として備わり、接続状態管理・再接続・タイムアウトを構造的に書ける。
- .NET 8はLTS(サポート ~2026年11月。長期運用を重視するなら .NET 10 LTSも検討)。`dotnet publish`で自己完結型単一EXEを配布可能。
- WPFはDirectX描画で長時間運転時も安定。ライセンス費ゼロ、CIが `windows-latest` で完結。
- Qtは商用ライセンスかGPLで、社内監視制御アプリの配布形態に制約が出る可能性。MFC/Win32は新規開発で選ぶ理由がない。

**注意点:** READMEに「C言語」との記述があるため、C言語へのこだわりがあるなら代替案として「**通信コアのみC(DLL) + GUI層はC#(P/Invoke)」** もあり得るが、デバッグ境界が増え保守性は下がる。まず言語方針の承認を求める。

### 4.3 推奨内部構成(案C採用時)

```
MonitoringApp/
├── src/
│   ├── Core/                 # ポーリングエンジン・状態機械・ドア開放監視(GUI非依存)
│   ├── Net/                  # TCPクライアント、シーケンス照合、タイムアウト、自動再接続(指数バックオフ)、KeepAlive、通信ログ(GUI非依存)
│   ├── Protocol/             # フレーム/メッセージ定義・エンコード/デコード・CRC16
│   └── App/                  # WPFアプリ(単一EXE)。user_themes.jsonでユーザー毎の外観を切替
├── tests/
│   ├── Monitoring.UnitTests/        # Protocol/Coreの単体試験
│   ├── Monitoring.IntegrationTests/ # 実TCPループバック結合試験(切断/再接続/異常パケット)
│   ├── LongRun/                     # 24時間連続運転試験ランナー
│   └── FakeDevice/                  # 試験用デバイスシミュレータ(故障注入可)
├── docs/
└── .github/workflows/               # build + test (windows-latest)
```

設計原則:
- Net/Protocol/CoreはUI非依存のクラスライブラリ。GUIは`DeviceMonitor`のイベント経由でのみ状態を受け取る(UIスレッドでのブロッキングI/O禁止)。
- **ユーザー別の外観**: 単一のWPFアプリが `user_themes.json` の「Windowsユーザー名 → テーマ(アクセント色・ロゴ画像・タイトル接尾辞、`*`フォールバック)」を読み、表示イメージのみユーザー毎に切り替える。アプリ本体・通信層は全ユーザー共通。

## 5. テスト戦略

| 試験種別 | 内容 | ツール・方法 | 実行タイミング |
|---|---|---|---|
| 単体試験 | Protocolのエンコード/デコード、フレーミングの境界処理、状態機械の遷移、再接続バックオフ | xUnit + Moq。通信は`IDeviceClient`抽象でモック | CIの毎PR |
| 結合試験 | 実TCPストリームで疑似デバイスと送受信。部分受信・パケット分割を意図的に再現 | FakeDevice(テスト用TCPサーバ)を試験内で起動 | CIの毎PR |
| 長時間試験 | 24〜72h連続運転。メモリ・ハンドル・スレッド数を定期記録し傾向評価 | 専用ワークフローをスケジュール実行。PerfCounter/メモリログ | 週次またはPhase4以降 nightly |
| Ethernet異常試験 | ①ケーブル抜け相当(サーバ強制切断)②TCP RST③応答遅延④ゴミパケット/CRC破損⑤パケットロス | FakeDeviceに故障注入機能。必要ならWindows側で clumsy/netem相当を適用 | CI(PR) + nightly |
| 自動試験(GUI) | 画面起動→接続→コマンド送信→切断表示までを自動操作 | FlaUI または WinAppDriver(WPFのUI Automation対応) | nightly。CIはビルド+非GUI試験まで |

CI方針: PRごとに `build → unit → integration → static analysis (Roslyn analyzers / optional: security)`。長時間試験とGUI自動試験はnightlyに分離し、PRを遅くしない。

## 6. プロダクトオーナーへの確認事項 — 回答済み(2026-11-02)

1. **言語方針**: ✅ **C# (.NET 8 + WPF) 承認**
2. **対向デバイス通信**: ✅ **TCP/IP。本アプリ側からのポーリング(request/response)。自動再接続・KeepAlive・通信ログ保存**(当初UDP指示→2026-11-02の構成指示によりTCPに変更)
3. **監視項目**: ✅ **鍵の状態、ドア開閉状態(開きっぱなし監視を含む)、鍵用カードリーダー**
   **制御項目**: ✅ **鍵(施錠/解錠)**
4. **運用形態**: ✅ **24時間常時監視**
5. **GUI構成**: ✅ **ユーザー毎に表示イメージを変えるだけでよい(アプリ本体は単一、ユーザー別テーマ/ロゴ切替)** — 当初プラグイン構成で起案したがPO指示によりシンプル化

上記を受け、`docs/protocol_spec.md` にTCPポーリングプロトコル仕様書を起案した。追加の構成指示(RULES.md)により、警告ゼロ・静的解析・フォーマット統一・Ethernet必須試験(通信断/再接続/タイムアウト/異常パケット/相手停止/再接続100回/24h)も実装した。

2026-11-02 設計承認時の追加要件(回答済み): **複数デバイス監視は必須**(`appsettings.json` の `Devices` 配列でデバイス毎に独立したクライアント/モニタを生成、GUIはデバイスセレクタで切替)、**認証/暗号は必要**(TLS 1.2/1.3 + 証明書サムプリントピン留め + PSK相互認証ハンドシェイク。仕様は protocol_spec.md §9/§10)。
24時間常時監視の要件から、以下が特に重要となる:

- ポーリング応答なし → 接続状態を `Lost` に遷移しUIへ即通知
- 長時間運転のメモリ・ハンドルリーク監視(Phase 4の長時間試験で検証)
- ドア開きっぱなし: 開状態が設定時間(例: 60秒、設定可能)を超えたらアラート
- カードリーダー: デバイス側でイベントを保持し、ポーリング応答に含めて取得
